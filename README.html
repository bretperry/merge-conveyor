A local GitHub merge queue

Conveyor

Hand off the merge queue. Your agent opens the pull requests, a trusted reviewer clears the commits that should ship, and Conveyor waits for CI and merges eligible PRs one at a time.

Say you have three cleared PRs. One is ready, one is still testing, and one has a failing check. Conveyor can merge the ready PR, wait for CI on the updated base, and check the queue again on the next scheduled tick. The PR still testing can move once it meets the merge requirements. The failing PR stays blocked until someone fixes it. Your agent can move on to other work while Conveyor keeps checking the queue.

Your existing CI runs the tests and reports results to GitHub. Conveyor discovers open PRs from GitHub and uses those results to decide what can merge. Set up a scheduler and resume the worker to have it handle the routine polling and merge order while consent is active.

Check status and see what's next

Open a terminal in your configured Conveyor checkout. If you're setting it up for the first time, start with the quick start.

conveyor status          # Is the worker paused? When did it last run?
conveyor queue           # Which pull requests are waiting?
conveyor explain 42      # What's holding up PR #42? Use your PR number.
conveyor tick --dry-run  # What would the next tick do?

A newly configured worker may show this when you run conveyor status.

acme/widgets → main
Journal: ok
Last tick: none · last successful tick: none
Conveyor is paused.

The worker starts paused. Once it has run, status shows the last merge or branch update if one was recorded. When consent is active, status shows when it expires. Status also shows any in-flight operation or pending retry.

conveyor status --json
conveyor status --config /absolute/path/to/config.json

Use the first command in scripts and the second if you keep your config outside the checkout. See examples for every command.

Conveyor is a local CLI and JavaScript library, using your checkout, GitHub access, and scheduler.

Know the boundary: Conveyor is not a hosted service or a multi-worker queue. Run one active worker per repository from a persistent, trusted, clean checkout. You supply the scheduler and keep the base branch current. GitHub branch protection remains the final authority.

Quick start

Conveyor uses the GitHub CLI (gh) for GitHub access. Build and install the package locally, prepare a dedicated checkout, verify access, then begin with read-only previews.

  1. Install prerequisites. Use Node.js 22 or later, Git, and gh. Authenticate gh against github.com with an account that has the access you intend to use.
  2. Build and install. From the Conveyor source checkout:
npm pack

# In a separate directory; use the tarball path npm pack printed.
install_dir=$(mktemp -d)
npm install --prefix "$install_dir" /absolute/path/to/merge-conveyor-0.1.0.tgz
export PATH="$install_dir/node_modules/.bin:$PATH"
conveyor --version
  1. Prepare a worker checkout. Use a dedicated, persistent clone with a GitHub origin, no submodules, and a clean worktree on the configured base branch at its current tip. Run Conveyor from this checkout.
  2. Configure it. Copy examples/conveyor.json to .conveyor.json at the checkout root. Set clearancePublisherId to the numeric GitHub ID of the trusted reviewer. You can get the authenticated account's ID with gh api user --jq .id. Keep the config ignored, or store it elsewhere and pass --config /absolute/path/config.json to every command.
  3. Protect the base branch. Require strict checks that apply to the worker identity, deny that identity bypass rights, configure an allowed merge method, and ensure a successful GitHub Actions push workflow exists for the current base tip. Restrict the worker's merge permission to the configured base branch.
  4. Check what Conveyor can see while it is paused. In the dedicated clone of the repository whose PRs you want to manage, authenticate gh as the account the worker will use. These read-only checks show what Conveyor can see with that account's permissions.
conveyor doctor

Check GitHub access, required checks, and the base workflow. Address any FIX lines before enabling the worker.

conveyor queue

Confirm the repository shown at the top and pick an open PR from the list. The queue covers the configured base branch. An empty queue is expected if no PRs target that branch.

conveyor explain 42

Replace 42 with a number from your queue. Run this to see the PR's current commit, check results, and anything it still needs before the worker can act.

  1. Review and clear the exact head. Inspect PR 42's full current head SHA. Authenticate gh as the configured trusted publisher and record clearance for that SHA:
conveyor clear 42 <full-reviewed-sha>

Replace 42 with the PR number you chose and <full-reviewed-sha> with the full SHA of the commit you reviewed. Clearance is scoped to that PR, commit, and configured base. A changed head requires fresh review and clearance.

  1. Preview the first action when you're ready to enable merges. Switch back to the worker credential and grant consent. Then ask Conveyor which PR it would act on, if any.
conveyor resume
conveyor tick --dry-run

A dry run previews the next action without merging or updating a branch. If the preview shows the action you intend to take, run a real tick to attempt it.

conveyor tick

Consent lasts eight hours by default. Stop it earlier with conveyor pause. Before scheduling recurring ticks, arrange to fast-forward the clean checkout when the remote base advances. Conveyor checks the checkout; it does not pull it forward.

JSON results and exit codes

Each JSON command writes one JSON Result to stdout. Progress messages, when shown in an interactive terminal, go to stderr. A result has one of these shapes:

{"ok":true,"value":{"repo":"owner/repo","base":"main","complete":true,"nextActionKnown":true,"nextAction":{"kind":"merge","number":42,"headSha":"…"},"entries":[],"globalBlockers":[]}}

{"ok":false,"error":{"code":"github_error","message":"…","retryAt":"…"}}
ExitMeaning
0A result was returned. A successful result may still say idle, blocked, incomplete, or unhealthy diagnostics.
1Operation error, unhealthy doctor, or corrupt status.
2Invalid command, option, or input.
3A tick or clearance write could not be confirmed. Reconcile with GitHub before retrying.

Do not treat a null nextAction as an empty queue unless complete and nextActionKnown are both true and there are no blocking conditions. Handle unfamiliar reason and error codes as displayable strings.

How a safe run works

  1. Inspect. doctor reports visible prerequisites; queue shows scheduling state; explain gives one PR's evidence.
  2. Review. A trusted publisher checks the exact full head SHA and records clearance with clear. Clearance does not cover later commits.
  3. Consent. An operator runs resume. The worker starts paused, and consent expires after the configured window.
  4. Preview. tick --dry-run shows the proposed action without writing. It is a snapshot, not a guarantee.
  5. Act once. A real tick rechecks current evidence and attempts at most one merge or update. GitHub can still reject a write if repository state or rules change.
  6. Reconcile and repeat. Check status and queue. If a write is unknown, inspect GitHub and follow recovery steps before another write.

How Conveyor decides what is next

Conveyor reads open pull requests and their checks, branch relationship, review/clearance evidence, and repository protection. It reports each entry as ready, waiting, blocked, or unknown. The queue is ordered by the scheduler evidence available to Conveyor, followed by entries that cannot be ranked. Reasons are returned as codes and human-readable messages.

Conveyor acts only when evidence is sufficient and the configured policy allows it. Missing or partial evidence can make the next action unknown. A branch update is disabled unless autoUpdate is enabled. Sensitive-path holds require a separate approval record: the standalone CLI/API does not provide a command to grant that approval, and clear is not a substitute.

What the preview tells you

tick --dry-run returns a queue snapshot with the proposed nextAction. A paused worker can still show PR details but has no active action. Between preview and tick, checks, heads, base, permissions, or queue order can change; the real tick performs its own checks.

Limits and operating boundaries

  • Reads have a 15-second and 160-command budget, inspect up to 200 open PRs and up to 99 check contexts per PR.
  • A PR exceeding the 300-file pinned-comparison limit cannot be relied on for a complete comparison; split it before relying on automated inspection/action.
  • Incomplete evidence is not an empty queue. Fix access or reduce the input, then inspect again.
  • Use one active worker per repository. Concurrent workers can race.
  • The checkout must be clean, on the configured base branch, current with its remote base tip, and have no submodules.
  • Conveyor does not update the worker checkout when the base advances. Fast-forward it while no tick is running.
  • GitHub's merge API pins the PR head SHA but does not pin the target branch. Restrict the worker's merge permission to the configured base in GitHub rules.
  • Read-only operations need visibility into the repository, PRs, checks, Actions, and branch protection. Clearance requires the trusted publisher identity and commit-status creation. The worker needs merge permission, and update permission if branch updates are enabled.

JavaScript API

The package exports createClient, the legacy createConveyor adapter, and EXIT_CODES. The typed declarations in src/index.d.mts are the authoritative detailed reference.

import { createClient } from "merge-conveyor";

const client = createClient({ cwd: "/path/to/worker-checkout" });
const result = await client.queue();

if (!result.ok) {
  console.error(result.error.code, result.error.message);
} else {
  const { complete, nextActionKnown, nextAction, entries } = result.value;
  console.log({ complete, nextActionKnown, nextAction, entries });
}

Every operation returns Promise<Result<T>>, shaped as { ok: true, value } or { ok: false, error }. A successful call can describe a blocked, incomplete, or unknown state. Check complete, nextActionKnown, and globalBlockers before interpreting a null next action as an empty queue.

createClient accepts cwd, configPath, and a config object override. It also accepts synchronous hooks:

  • policy({repo, base, action, paths}) must return true to allow a worker write. It can veto, but cannot override holds or GitHub rules.
  • notify({repo, base, message}) receives worker reports and alarms. Messages may include PR numbers, titles, failure details, and operational state. Protect the destination. Failed delivery is queued for retry.

The standalone CLI does not configure a notification callback. The legacy createConveyor(config) adapter remains available for integrations; its callback contract and legacy exit behavior are separate from createClient.

Recovery and uncertain writes

An unknown outcome or exit code 3 means the response was not confirmed. GitHub may have accepted the write. Do not immediately repeat it.

  1. Stop the scheduler and run conveyor pause. Ensure no worker is still active.
  2. Inspect the PR, head, base, merge state, clearance status, and GitHub history. Use conveyor status to inspect local journal state.
  3. If the journal shows an in-flight operation, restore GitHub access and run one manual tick with the same checkout/config to reconcile. A paused tick can reconcile an earlier write without submitting another one.
  4. Recheck GitHub and status. If uncertain, keep the scheduler stopped and escalate to the repository maintainer.

Journal, logs, lock, consent, and approval records are stored in the Git common directory, normally conveyor.json and conveyor.log. stateName changes the stem. Back up these files before maintenance. Do not delete a journal or lock until the operation is reconciled and all worker processes have stopped. See Operator recovery for stalled workers, corrupt state, notification delivery, upgrade, and rollback guidance.

Security setup

  • Use a dedicated trusted checkout and protect its credentials and Git common directory. Local operators with write access there can pause or resume the worker.
  • Use separate trusted publisher and worker identities as your operating model requires. The publisher records clearance; the worker performs the merge/update under GitHub's rules.
  • Do not grant the worker branch-protection bypass rights. Apply strict required checks to the worker identity and restrict merge permissions to the configured base.
  • Verify permissions, required-check behavior, merge method, and retargeting protections in a disposable repository before enabling recurring ticks.
  • Use doctor as a visible prerequisite check, not a replacement for reviewing your GitHub rules and access model.
